# 代码审核与技术债

## 审核范围

本次审核追踪了截屏坐标、OCR 进程配置、结果解码、结构归一化、翻译分段、覆盖窗口、自动化接口、配置写入、构建类型与应用内更新。数据流与首次复现见 `project-review.md`，原始截图的识别验收见 `ocr-quality.md`。

架构检查覆盖 330 个 Python 文件、1971 条依赖。八项依赖约束通过：业务与内核保持 Qt 隔离，OCR 子进程保持业务隔离，标准库自动化客户端保持独立。新增的图像外观分析只在主进程归一化阶段使用，没有扩展跨进程结果协议。

## 已处理的问题

1.1 在分发的解释器目录补齐锁定版本的 MSVC 运行库，独立推理进程可以在导入 Qt 之前加载 CTranslate2 和 Paddle。解释器清单启用 UTF-8 进程代码页；SentencePiece 直接接收 Python 读取的模型字节，中文模型路径完成真实推理验证。

主题标签按深浅色变化信号的新值立即刷新正文颜色，避免主题切换时短暂保留旧颜色。词典语言对每次按实际文件列表判断，目录时间戳相同的增删操作也立即反映；模型内容的解压与解析仍保留缓存。

配置修改回执使用请求号关联实际写入结果，替代监听任意配置修订号的做法。并发成功、并发拒绝、无变化均由真实配置服务测试约束，自动化调参可以依据返回结果开始下一步。

同一会话重新识别时发布 `OcrStarted`，会话记录清除旧失败、旧翻译进度和完成时间。命名管道的长度检查同时覆盖已带换行与尚未收完的请求。

识别验收建立了 98 个人工文字单元，分别约束内容、召回、粘连、拆碎与位置。缓存保存源图片 SHA-256，防止有损转换图片的旧识别结果与原始 PNG 混用。主进程按图像前景、字号、间距和几何关系整理控件，纯数字与符号在覆盖窗口中保留原像素。

显卡运行库的目录发布增加了 Windows 错误 5、32、33 的有限重试。真实文件系统连续安装 300 次，出现 3 次首次改名拒绝，均在等待 25 毫秒后成功。回归覆盖短暂拒绝后的成功、持续权限错误和其他错误立即失败；总等待上限为 1.575 秒，目录发布仍使用原子改名，持续失败时清理临时目录并报告磁盘错误。

## 需要继续处理的项目

### 屏幕样本覆盖

当前质量门槛覆盖两页英文界面与繁体中文参考布局。菜单间距、笔画粗细和文字框外扩均参与分段判断；两页上的通过结果不足以覆盖中文正文、阿拉伯文、代码编辑器、透明窗口和混合字号文档。

后续扩展样本应保留原始无损图片，按语言、字号、缩放比例和背景类型分组。每次调整外观阈值，同时检查现有段落样本与新增截图的内容损失、误合并和误拆分。评分符号与图标误识别还要检查实际覆盖图：纯字母图标仍会被当作待翻译内容，当前回归报告保留这些额外输出。

### 服务器检测输出的碎片合并

beta.3 的横向拼行使用着墨高度与框间距。服务器检测器把正文拆成单词框时，`scenes` 与 `laying` 的着墨高度分别为 13 和 22 像素；同字号中的字形差异超过原有高度容差，漏词还会产生超过横向上限的空隙。横向拼接失败后，纵向合并形成跨行的局部小段，阅读顺序随之改变。原始结果中的漏词属于检测损失，后处理无法补回。

验收分别检查原始行框与最终段落，量化检测漏字与后处理顺序错误。当前发布保留默认轻量模型；使用服务器模型时可显式选择已验证的检测尺度，完整对照见 `server-ocr-analysis.md`。

1.0 使用框高与笔画共同判断字号，并为漏检词的间隙和候选栏缝补充原图证据。默认服务器组合的正文生产误差从 85 降到原始漏检的 18；长边最多 1280 的正文误差从 12 降到 0。外扩 1.2 的可用文字顺序已正确，正文仍拆成六段。长边最多 960 的服务器配置在两页的 98 个标注单元上全部召回，无误合并或误拆分。继续改进外扩较小配置时，需要同时保持真实栏缝、导航控件和不同字号的边界。

### Windows OCR 的默认识别语言

Windows OCR 的 `auto` 按系统用户首选语言创建识别器。本机的可用识别器为 en-US 与 zh-Hans-CN，首选为 zh-Hans-CN。用实际 `auto` 配置处理两张英文原图，归一化文字准确率分别为 94.43% 和 98.23%，单元召回率分别为 87.3% 和 89.5%；显式选择英文时对应准确率为 99.36% 和 99.47%。

1.0 增加英文与中日文的互补识别，显式语言选择仍只运行一种识别器。真实子进程的自动模式在两张英文原图上分别达到 99.36% 和 99.47%，与显式英文结果一致；召回率为 97.5% 和 100%。原始两张繁体中文图上，中文识别器已有的中日文词及其位置全部保留，评分星形误读出的重复汉字单独排除。这一检查约束内容保留，不把原始识别器的错字计为正确识别。

纯英文、纯中文、同一行混排、英文主体与中文标题四种合成截图通过真实系统 OCR 验证。完整应用的真实 Windows OCR 与本地 NMT 链路分别验证英文和自动配置，截图、翻译、覆盖、选择复制与键位操作均成功。SDK 仍会把“设置”误识别成分开的偏旁；这是原始中文识别的错误，互补选择保留原始候选，不能补出缺字。

自动模式在首选英文时只补充第一个已安装的中日文识别器，其他语种仍跟随系统首选。单个字、同形字符、带明显间距的重复文字与计数仍存在歧义。用户需要精确指定语言时可以选择该语言，PaddleOCR 和 RapidOCR 继续作为其他识别方案。

### Python 事件循环的内部接口

命名管道服务端使用 Windows Proactor 事件循环的 `_proactor`，自行创建带当前用户访问控制的管道，再将异步读写交给事件循环。该属性属于 CPython 内部接口；项目将 Python 固定在 3.13，现有真实管道测试约束这个组合。

升级 Python 或 qasync 时，应先运行管道接受、读写、断开、重复启停和关闭自身接口的集成测试。适配代码集中在 `server.py` 的 `_Proactor` 与 `_proactor_of`，版本适配应保留这一隔离边界。

### 首次运行引导与诊断导出

`lst/ui/onboarding/__init__.py` 明确记录首次运行引导只覆盖本地翻译模型下载，GPU、CUDA、Ollama 检测与配置首个引擎尚未接入。托盘的诊断导出项保持禁用，`lst/ui/tray/presenter.py` 尚未定义对应命令。这两项属于已呈现在代码与入口中的未完成产品链路。

完成引导时，需要串联检测、设置写入、运行环境安装和首次实际调用；完成诊断导出时，需要定义去除凭据的配置、版本和日志文件格式，再接通设置与托盘入口。
