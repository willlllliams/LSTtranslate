# 代码审核与技术债

## 审核范围

本次审核追踪了截屏坐标、OCR 进程配置、结果解码、结构归一化、翻译分段、覆盖窗口、自动化接口、配置写入、构建类型与应用内更新。数据流与首次复现见 `project-review.md`，原始截图的识别验收见 `ocr-quality.md`。

架构检查覆盖 329 个 Python 文件、1963 条依赖。八项依赖约束通过：业务与内核保持 Qt 隔离，OCR 子进程保持业务隔离，标准库自动化客户端保持独立。新增的图像外观分析只在主进程归一化阶段使用，没有扩展跨进程结果协议。

## 已处理的问题

配置修改回执使用请求号关联实际写入结果，替代监听任意配置修订号的做法。并发成功、并发拒绝、无变化均由真实配置服务测试约束，自动化调参可以依据返回结果开始下一步。

同一会话重新识别时发布 `OcrStarted`，会话记录清除旧失败、旧翻译进度和完成时间。命名管道的长度检查同时覆盖已带换行与尚未收完的请求。

识别验收建立了 98 个人工文字单元，分别约束内容、召回、粘连、拆碎与位置。缓存保存源图片 SHA-256，防止有损转换图片的旧识别结果与原始 PNG 混用。主进程按图像前景、字号、间距和几何关系整理控件，纯数字与符号在覆盖窗口中保留原像素。

显卡运行库的目录发布增加了 Windows 错误 5、32、33 的有限重试。真实文件系统连续安装 300 次，出现 3 次首次改名拒绝，均在等待 25 毫秒后成功。回归覆盖短暂拒绝后的成功、持续权限错误和其他错误立即失败；总等待上限为 1.575 秒，目录发布仍使用原子改名，持续失败时清理临时目录并报告磁盘错误。

## 需要继续处理的项目

### 屏幕样本覆盖

当前质量门槛覆盖两页英文界面与繁体中文参考布局。菜单间距、笔画粗细和文字框外扩均参与分段判断；两页上的通过结果不足以覆盖中文正文、阿拉伯文、代码编辑器、透明窗口和混合字号文档。

后续扩展样本应保留原始无损图片，按语言、字号、缩放比例和背景类型分组。每次调整外观阈值，同时检查现有段落样本与新增截图的内容损失、误合并和误拆分。评分符号与图标误识别还要检查实际覆盖图：纯字母图标仍会被当作待翻译内容，当前回归报告保留这些额外输出。

### 服务器检测输出的碎片合并

`GeometricMerger` 的横向拼行使用着墨高度与框间距。服务器检测器把正文拆成单词框时，`scenes` 与 `laying` 的着墨高度分别为 13 和 22 像素；同字号中的字形差异超过当前高度容差，漏词还会产生超过横向上限的空隙。横向拼接失败后，纵向合并形成跨行的局部小段，阅读顺序随之改变。原始结果中的漏词属于检测损失，后处理无法补回。

后续需区分词级检测与行级检测的输入，先恢复可靠基线，再判断真正的跨栏关系。验收应同时检查服务器原始行框与最终段落，分别量化检测漏字与后处理顺序错误。当前发布保留默认轻量模型，服务器对照实验与输入尺寸结论记录在 `server-ocr-analysis.md`。

1.0 开发中的改动使用框高与笔画共同判断字号，并为漏检词的间隙和候选栏缝补充原图证据。默认服务器组合的正文生产误差从 85 降到原始漏检的 18；长边最多 1280 的正文误差从 12 降到 0。外扩 1.2 的可用文字顺序已正确，正文仍拆成六段。长边最多 960 的服务器配置在两页的 98 个标注单元上全部召回，无误合并或误拆分，详细对照和边界见 `server-ocr-analysis.md`。

### Windows OCR 的默认识别语言

Windows OCR 的 `auto` 按系统用户首选语言创建识别器。本机的可用识别器为 en-US 与 zh-Hans-CN，首选为 zh-Hans-CN。用实际 `auto` 配置处理两张英文原图，归一化文字准确率分别为 94.43% 和 98.23%，单元召回率分别为 87.3% 和 89.5%；显式选择英文时对应准确率为 99.36% 和 99.47%。

1.0 开发版增加英文与中日文的互补识别，显式语言选择仍只运行一种识别器。真实子进程的自动模式在两张英文原图上分别达到 99.36% 和 99.47%，与显式英文结果一致；召回率为 97.5% 和 100%。原始两张繁体中文图上，中文识别器已有的中日文词及其位置全部保留，评分星形误读出的重复汉字单独排除。这一检查约束内容保留，不把原始识别器的错字计为正确识别。

纯英文、纯中文、同一行混排、英文主体与中文标题四种合成截图通过真实系统 OCR 验证。完整应用的真实 Windows OCR 与本地 NMT 链路分别验证英文和自动配置，截图、翻译、覆盖、选择复制与键位操作均成功。SDK 仍会把“设置”误识别成分开的偏旁；这是原始中文识别的错误，互补选择保留原始候选，不能补出缺字。

自动模式在首选英文时只补充第一个已安装的中日文识别器，其他语种仍跟随系统首选。单个字、同形字符、带明显间距的重复文字与计数仍存在歧义。用户需要精确指定语言时可以选择该语言，PaddleOCR 和 RapidOCR 继续作为其他识别方案。

### Python 事件循环的内部接口

命名管道服务端使用 Windows Proactor 事件循环的 `_proactor`，自行创建带当前用户访问控制的管道，再将异步读写交给事件循环。该属性属于 CPython 内部接口；项目将 Python 固定在 3.13，现有真实管道测试约束这个组合。

升级 Python 或 qasync 时，应先运行管道接受、读写、断开、重复启停和关闭自身接口的集成测试。适配代码集中在 `server.py` 的 `_Proactor` 与 `_proactor_of`，版本适配应保留这一隔离边界。

### 首次运行引导与诊断导出

`lst/ui/onboarding/__init__.py` 明确记录首次运行引导只覆盖本地翻译模型下载，GPU、CUDA、Ollama 检测与配置首个引擎尚未接入。托盘的诊断导出项保持禁用，`lst/ui/tray/presenter.py` 尚未定义对应命令。这两项属于已呈现在代码与入口中的未完成产品链路。

完成引导时，需要串联检测、设置写入、运行环境安装和首次实际调用；完成诊断导出时，需要定义去除凭据的配置、版本和日志文件格式，再接通设置与托盘入口。

### GPU 与安装维护的真机覆盖

本轮全量回归为 4431 项通过、13 项跳过，显卡运行库安装有一项因 Windows 目录改名拒绝而失败。该问题经上述真实文件系统循环复现后修复，显卡运行库模块的 18 项测试全部通过。新增源图缓存校验及服务器尺度样本另经 14 项识别保真度回归验证。完整执行中其余测试已通过；修复后的验证针对改动所属模块进行。

普通版与开发版使用同一份暂存程序，安装标记决定自动化默认开关及更新安装包。构建自检覆盖真实启动器、主进程导入、五份带哈希的 OCR 依赖清单与 uv 可执行文件。现有测试覆盖构建类型、包名、校验文件与更新资产选择。

CUDA 不可用时对应推理测试跳过。当前环境中的验证也不能代替每种 GPU 运行环境的实际安装、升级与卸载。后续发布验证应增加干净 Windows 用户环境，实际安装普通版和开发版，再检查覆盖升级、显式配置保留、模型目录迁移及卸载数据选项。

Argos 解压目录、OCR 模型目录、OCR 运行环境与显卡运行库现共用有限重试的原子目录发布。真实 Windows 测试用读取权限打开目录，不允许删除共享，使改名返回共享冲突；释放句柄后下一次改名成功，持续占用时源数据保留。删除共享也影响改名，参数约定见 [Microsoft CreateFile 文档](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)。

审核还发现 OCR 换版本原先先删除旧运行环境，再发布新目录。新目录改名失败会丢失旧环境。现在旧环境保留在 `site.previous`，新环境和最终安装标记使用相同的安装编号；失败或重启时按编号与清单哈希决定恢复旧环境还是保留已提交的新环境。相同版本清单的重装也分别识别提交状态。

原生 Windows 的新环境目录锁与安装标记文件锁均经过完整引擎模块测试：失败后恢复原环境和原安装标记，旧版本保持可运行。启动恢复覆盖旧目录已移走、新目录已发布、安装标记已提交三个中断点，并分别检查相同与不同版本清单。备份清理失败保留已提交的新版本，后续启动继续清理。回滚后的同版本进程重启也有组合根回归。
